## Context

仓库处于 WIP 阶段，工作区同时包含已修改的跟踪文件和未跟踪的 OpenSpec 配置。用户要求只总结已提交代码，因此分析必须与当前工作区隔离，并可追溯到明确的提交。`HEAD` 当前存在包迁移未闭合的问题，不适合把代码结构等同于已验证的运行能力。

## Goals / Non-Goals

**Goals:**

- 以固定提交 `29f9faf` 为唯一代码事实来源，生成可复现的架构与实现状态摘要。
- 明确区分代码缺口、环境缺口、占位实现和未来路线图。
- 产出可归档的 proposal、design、tasks，并保持用户未提交文件原样。

**Non-Goals:**

- 不修复构建、导入路径、执行器或沙箱依赖。
- 不运行或验证 LLM、工具执行、MCP、会话持久化等外部交互。
- 不生成正式 capability spec，也不修改主 specs。

## Decisions

- **使用 `git archive HEAD` 解包到 `/tmp` 后分析。** 这样不会读取工作区中的未提交内容，也不会调用分支切换或工作树写入操作。替代方案是直接读取工作区并按 `git diff` 人工排除，但容易遗漏未跟踪文件，故不采用。
- **以构建结果作为实现状态证据。** 在隔离副本中执行 `env GOCACHE=/tmp/agent_cli_go_cache go test ./...`。结果同时记录两类失败：代码仍引用已移动的工具包路径，以及环境缺少 `libseccomp` pkg-config 元数据；不把环境问题误判为代码问题。
- **本 change 不创建 spec。** 纯文档基线没有行为变化，且 `HEAD` 尚不能完整构建；把 WIP 结构写成 Requirement 会产生虚假的已实现契约。归档时使用 `skip_specs`，将后续修复留给独立 change。
- **摘要按职责和主数据流组织，而不是逐文件复述。** 保留关键入口、模块边界、接口骨架、构建证据和风险，便于后续按独立需求拆分修复任务。

## Risks / Trade-offs

- [`HEAD` 后续变化导致摘要过期] → 在 proposal 中固定提交哈希；未来更新基线时创建新 change。
- [构建失败受当前 Linux 依赖环境影响] → 分开记录代码导入错误与 `libseccomp` 环境错误，不能只凭一次失败判断全部实现不可用。
- [跳过 specs 会减少正式行为契约] → 这是有意取舍；待对应模块修复并具备可测试行为后，再通过独立 change 建立 capability。
- [Git 对象分析成本高于直接读工作区] → 用一次性临时快照换取明确的未提交隔离，不影响仓库内容。

## Migration Plan

无需运行时或数据迁移。文档完成后执行 `openspec validate` 和 `openspec archive --skip-specs`；归档只移动本 change 文档，不触碰其他工作区文件，回滚方式是恢复对应归档目录及其文件。
